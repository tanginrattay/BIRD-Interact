# 项目接手与文档维护规则

本目录是 BIRD-Interact-ADK：用户借助 BIRD-Interact 测评框架研究自己的多轮 Text-to-SQL agent scaffold。保留原框架的代码布局；研究文档入口在 `agent/`，被测 agent 代码在 `system_agent/`。不要把维护文档理解成重构代码或修改测评协议。

## 新对话如何阅读

1. 先读 [agent/README.md](agent/README.md) 和 [agent/STATUS.md](agent/STATUS.md)，理解研究目标、当前进度和接下来要做的事。
2. 研究方案、实现 scaffold 时读 [agent/DESIGN.md](agent/DESIGN.md)；实验比较、分析结果时读 [agent/EXPERIMENTS.md](agent/EXPERIMENTS.md)；运行、调试、修改代码时读 [agent/DEVELOPMENT.md](agent/DEVELOPMENT.md)。按任务读取对应证据，不要求每次通读全部历史。
3. 修改或运行前核对实际 cwd、Git 分支、工作区变化及相关代码。文档中的核查日期和分支只是快照，不能代替现场状态。
4. `agent/` 只维护上述五份活跃文档。旧材料已移入 `trashbin/`，默认不读、不扫描，不把其中的“当前”“最新”当成现状。

## 五份活跃文档的分工

| 文件 | 唯一职责 | 更新时机 |
| --- | --- | --- |
| README.md | 研究目标、范围、导航 | 项目定位或文档体系变化 |
| STATUS.md | 当前状态、重要结论、待办、阻塞 | 每次有实质进展的工作结束时 |
| EXPERIMENTS.md | 实验摘要、配置身份、结果和证据入口 | 新实验完成、结果更正、分析结论变化 |
| DESIGN.md | 当前机制、假设、已确认决策、待讨论方案 | 设计讨论或实现状态变化 |
| DEVELOPMENT.md | 代码地图、开发和运行方法、复现约定 | 代码入口、环境要求、操作方式变化 |

成绩表只维护在 EXPERIMENTS；STATUS 摘要并链接。设计理由只在 DESIGN 展开。详细报告和原始轨迹留在原实验目录，不复制到接手文档。文档使用中文，文件名、代码符号保留原文。

## 当用户说“根据本对话内容，更新 agent/”

这是一项完整的文档维护指令。自行完成以下步骤，不要求用户指定文件、逐条提供摘要或手动检查：

1. 阅读当前五份文档，回顾本对话中的用户决定、完成的工作、实际结果、失败或取消事项和未完成任务。检查本次改动以及相关产物；只检查与更新有关的内容。
2. 分清用户已决定的方向、助手提出但未被采纳的建议、已经实现的行为、已经验证的结论。讨论不等于决定，代码完成不等于真实实验通过。网页聊天转述可以作为用户意图来源；其中的实验事实仍应与本地证据核对。
3. 按上表更新受影响文件。替换过时的当前描述，删除已完成的待办；仍有解释价值的旧结论保留为简短决策记录或实验条目。不要每轮新增 HANDOFF、会话流水账或重复报告。无变化的文件不必重写。
4. 对新实验记录日期、实验 ID、题集及数量、Agent/Simulator、方案和源码身份、指标分母、错误/未完成情况、原始结果与分析入口。用源码快照或 commit+diff 标识实验实现，不用今日分支 HEAD 代替当时版本。
5. 每项重要结论附本地证据链接。说明“观察到什么”“尚不能推出什么”；缺失记为 `UNKNOWN` 或 `unavailable`，待验证明确标注。不得补造结果、费用、运行验证、语义指标或当前配置。
6. STATUS 保持简短：记录最近核查日期、研究重点、最新进展、真正的下一步和阻塞。用户未确认的下一步写成待讨论，不替用户选定研究方向。
7. 自行检查五份文件之间是否矛盾、相对链接是否存在、指标是否与来源一致、是否泄露密钥、是否把旧配置写成现状。检查 Git diff 确认没有越界改动。纯文档更新无需启动服务、运行模型或重跑实验。
8. 完成后简短报告更新内容、仍缺的上下文和是否提交。只有缺失信息会改变关键事实或用户意图时才提问；其余可完成部分先完成。不把普通核对工作交回用户。

用户只说“更新 agent/”时，默认只改这五份文档；改变文档体系才同步维护本文件。不要顺带移动旧报告、改代码/配置、修改结果、执行实验或提交 Git。明确授权另行覆盖这一默认范围。跨分支工作时读取目标分支已有文档，合并相关事实，不以当前分支覆盖其他实现，也不自动切换、合并或提交分支。

## 工作边界与保存规则

- `results/` 与 `trajectory_analysis/` 结构已被用户认可，不重新组织；分析任务优先追溯完整 session、工具事件和逐题证据。
- `trashbin/` 存放暂时丢过来、大概率没用的材料，已在 `.gitignore` 中；不自动清理，不把它当作可随 Git 恢复的备份。移入时严格保留项目根相对路径：`a/b.txt` → `trashbin/a/b.txt`，不加日期或批次包装目录，不静默覆盖同名目标。其 README 只写用途和规则，不维护内容清单。
- 保留用户已有未提交改动。不要为整理文档恢复、删除或提交他人的工作区变化。
- 文档维护默认不提交 Git；只有用户明确授权提交或跨分支同步时才执行。共享文档区分各分支实现，不能因同步文档而合并实验代码。
- 删除文件或目录禁止使用任何形式的 `rm`，必须用 `trash-put`；不可用时停止删除并告知用户，不得改用永久删除方式。
- 不把 `.env`、API key、认证头或其他秘密写进文档、日志或提交。当前配置以经过脱敏的实际配置和运行证据为准。
